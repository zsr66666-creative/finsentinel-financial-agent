# 第十三周复核事务与反馈闭环设计

## 目标

为告警建立可审计的人工复核闭环：用户可以确认、驳回或修改告警；每次操作追加保存，具备事务和幂等保证，并可生成待审核回归候选。

## 范围

- 支持 `confirm`、`reject`、`modify` 三种反馈动作。
- `reject` 和 `modify` 必须提供原因；`modify` 还必须提供修改内容。
- 反馈历史追加保存，不覆盖原始告警结果。
- 告警当前状态与反馈记录在同一事务中更新。
- 重复请求使用幂等键，不能重复产生业务记录。
- 反馈只生成 `pending_review` 回归候选，不能自动成为黄金标准。
- 前端复核队列刷新后保留状态，并展示历史。

## 状态与数据流

```text
告警 pending_review
  -> confirm -> confirmed
  -> reject  -> rejected
  -> modify  -> modified_pending_review

反馈记录（追加） -> 回归候选 pending_review -> 人工审核
```

每条反馈至少保存：`alert_id`、原结果版本、动作、原因、修改内容、幂等键、提交时间和审核者标识。告警详情继续引用原始证据和运行版本。

## API 契约

`POST /api/v1/alerts/{alert_id}/feedback`

请求字段：

```json
{"action":"confirm|reject|modify","reason":"...","modification":{},"idempotency_key":"..."}
```

成功响应返回当前告警状态、反馈记录和回归候选状态。非法动作、缺少原因、重复幂等键冲突和不存在告警分别返回结构化 4xx 错误。

## 事务边界

反馈插入、告警状态更新和回归候选创建必须在一个数据库事务中完成；任一步失败都回滚。历史反馈只允许追加，禁止更新或删除既有记录。

## 验收与限制

- 后端测试覆盖三种动作、校验、事务回滚和幂等。
- 前端测试覆盖提交、错误、刷新后状态和离线状态。
- 回归候选明确为人工待审核数据。
- 不引入 PostgreSQL、Redis、Arq 或自动金标准更新。
- 测试报告单独记录 Windows 临时目录权限导致的环境限制。
